# Pi0.5 on SM80 (A100 / A800)

Datacenter Ampere has BF16 tensor cores and no FP8 ones. `detect_arch()`
maps compute capability 8.0 to `"rtx_sm80"`, and two Pi0.5 frontends resolve
there:

| config | frontend | what it is |
|---|---|---|
| `pi05` | `Pi05TorchFrontendRtx` | the RTX frontend on its BF16 pipeline (the path Jetson Orin runs without its INT8 flags): FlashRT's own kernels, one captured graph per call |
| `pi05_isomorphic` | `Pi05TorchFrontendIsomorphic` | the same checkpoint on the arithmetic of its trainer: rollouts that FlashRT-Train's training forward reproduces bit for bit. See [pi05_isomorphic.md](pi05_isomorphic.md) |

Other configs are refused on SM80 at resolution: each needs a BF16 pipeline
validated there before it is listed.

## Build

CUTLASS v4.4.2 at `third_party/cutlass`, as on every target.

```bash
cmake -S . -B build -DGPU_ARCH=80 \
  -DFLASHRT_SLIM_BUILD=ON -DFLASHRT_ENABLE_PI05_SDE=ON \
  -DFA2_ARCH_NATIVE_ONLY=ON -DFA2_HDIMS='96;128;256' -DFA2_DTYPES='bf16'
cmake --build build -j2
```

`FLASHRT_ENABLE_PI05_SDE` builds the stochastic sampler's step kernel
(`sde=True`); leave it out for the ODE sampler alone. The slim build and the
FA2 restrictions only shorten the build.

## Use

```python
import flash_rt

model = flash_rt.load_model(checkpoint, config="pi05", framework="torch",
                            num_views=3)          # hardware="auto" resolves rtx_sm80
```

or the frontend directly, which also gives the rollout surface of
[rl_inference.md](rl_inference.md) (seeded noise, the stochastic sampler,
the denoise trace, `infer_batch`):

```python
from flash_rt.frontends.torch.pi05_rtx import Pi05TorchFrontendRtx

fe = Pi05TorchFrontendRtx(checkpoint, num_views=3, chunk_size=50, num_steps=10,
                          denoise_trace=True, sde=True)
fe.set_prompt("pick up the black bowl and place it on the plate")
fe.calibrate([observation])        # BF16: warms the buffers and captures the graph
out = fe.infer(observation, noise=noise)
```

## Readings

A800 80 GB, CUDA 12.3 toolchain, PyTorch 2.7.1 (cu126), the π0.5 base
checkpoint, three 224×224 views, action horizon 50, ten steps, a 13-token
prompt, random frames; medians of nine calls after a warm-up, the whole
`infer` / `infer_batch` call including host staging.

| batch | per call | per sample |
|---|---|---|
| 1 | 39.5 ms | 39.5 ms |
| 8 | 212.2 ms | 26.5 ms |
| 32 | 853.6 ms | 26.7 ms |

Within a process the same inputs give the same actions. Across processes:
the ODE sampler at batch 1 gave one result in four processes and the
stochastic sampler at batch 4 one result in six, while the stochastic
sampler at batch 1 gave three different results in six processes. The cause
was not isolated; the pipeline times its GEMM candidates at calibration and
keeps the fastest, which is a per-process choice.

**Against the reference arithmetic.** FlashRT-Train's forward is the openpi
PyTorch model's arithmetic at the level of that model's own rounding noise
(its documented equivalence), so it serves here as the reference. With one
prompt for every sample, the native pipeline's ten-step actions have cosine
0.9998–0.9999 with it (relative rms 1.2–2.2%), and its velocity at a
recorded state is 0.56–0.60% from it in relative rms. For comparison, the
openpi model recomputing its own rollout one sample at a time lands 0.30%
from itself.

**Mixed prompt lengths in a batch.** `set_prompt_batch` pads shorter prompts
with zero embeddings that the prefix attends to; there is no per-sample
prompt mask in the batched pipeline. With eight prompts of 5 to 19 tokens
in one batch the actions' cosine with the masked reference drops to 0.98
(relative rms about 20%). A batch whose prompts tokenize to one length is not
affected. The isomorphic frontend masks its padding.

`tools/check_pi05_isomorphism.py --native [--same-prompt]` reproduces these
readings.
