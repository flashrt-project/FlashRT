# Xiaomi-Robotics-1 on AMD gfx1151

FlashRT supports XR-1 through `flash_rt.load_model(config="xr1")` on ROCm
gfx1151. Two checkpoint formats are supported:

| Checkpoint | Inputs / camera order | Action output |
|---|---|---|
| `XiaomiRobotics/Xiaomi-Robotics-1-RoboCasa` | base 1, base 2, left wrist; 8-component proprioceptive state | `(10, 7)` |
| `XiaomiRobotics/Xiaomi-Robotics-1-5B` | ego, left wrist, right wrist; packed 60-component state | `(30, 60)` |

The 5B checkpoint is the published foundation policy for further post-training.
Its action normalization and state quantiles must come from the target
embodiment's data. The example below uses upstream `load_washer` demonstration
statistics to exercise inference; those statistics are not a general robot
calibration or evidence of task success.

## Installation

Requires an installed ROCm 7.2 toolkit, Python 3.12, and a visible gfx1151 GPU.
The setup script creates `.venv-xr1-runtime`, installs AMD's gfx1151-capable
PyTorch/torchvision/Triton wheels, pins Transformers to `4.57.1`, installs
FlashRT, and builds its standalone gfx1151 HIP extension:

```bash
bash scripts/amd/setup_xr1.sh
source .venv-xr1-runtime/bin/activate
export TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1
```

Set that variable before starting Python to use the ROCm 7.2 attention kernels
validated on this platform. Without it PyTorch uses available fallback kernels;
the model still runs, with different performance. Neither NVIDIA CUDA wheels
nor the upstream `flash-attn` package are required. The reference path also runs
without the FlashRT HIP extension.

The environment path and interpreter can be overridden with
`FLASHRT_XR1_ENV` and `FLASHRT_XR1_PYTHON`. ROCm PyTorch is intentionally installed
from AMD wheel URLs rather than allowing an optional extra to select a CUDA wheel.

## RoboCasa deploy checkpoint

Download the checkpoint at a fixed revision:

```bash
bash scripts/amd/download_xr1.sh robocasa
```

Inference accepts three RGB images as PIL images or HWC uint8 arrays. The state
uses the upstream RoboCasa ordering: seven joint positions and one gripper
position. It is padded to 60 components without state normalization, matching
the released RoboCasa processor.

```python
import numpy as np
import flash_rt

model = flash_rt.load_model(
    ".cache/xr1/robocasa", config="xr1", framework="torch",
    hardware="amd_rdna35", num_views=3, num_steps=5,
    use_fp8=False, attention="sdpa", fuse=True,
)
actions = model.predict(
    images=[base1_rgb, base2_rgb, left_wrist_rgb],
    prompt="pick up the red block",
    state=np.asarray(joint_and_gripper_state, dtype=np.float32),
)
assert actions.shape == (10, 7)
# Later calls can reuse the instruction while supplying the new observation.
actions = model.predict([base1_rgb, base2_rgb, left_wrist_rgb], state=new_state)
```

Deploy checkpoint custom code is loaded with `trust_remote_code=True`. The
provided download script pins the reviewed checkpoint revision
`82b7c2210c1a39fca4a87e681cffbbed134ccde0`.

## Published 5B checkpoint

Download weights and the Qwen3-VL processor/config, then attach embodiment data:

```bash
bash scripts/amd/download_xr1.sh 5b
python scripts/amd/prepare_xr1_5b.py \
    --checkpoint .cache/xr1/5b \
    --tokenizer .cache/xr1/qwen3vl-tokenizer \
    --stats /path/to/target_embodiment_stats.json \
    --embodiment my_robot
```

The statistics file must contain finite `mean`, `std` arrays shaped `(30,60)`
and `q01`, `q99` arrays shaped `(1,60)`. Alternatively, `--stats` accepts an
upstream XR-1 data YAML containing `data.params.train_datasets` with those keys.
The script copies only tokenizer/config files and creates `normalization.json`.
No additional Qwen model weights are needed: the 5B checkpoint contains its VLM.

```python
model = flash_rt.load_model(
    ".cache/xr1/5b", config="xr1", framework="torch",
    hardware="amd_rdna35", num_views=3, num_steps=5,
    attention="sdpa", fuse=True, use_fp8=False,
)
actions = model.predict(
    [ego_rgb, left_wrist_rgb, right_wrist_rgb],
    prompt="place the cup on the table", state=packed_state_60,
)
assert actions.shape == (30, 60)
```

State packing matches `xr1/mibot/utils/io.py` in upstream: up to seven left joints at
`0:7`, left gripper at `7`, up to seven right joints at `8:15`, and right gripper at `15`,
with the other state channels zero padded. State quantiles are applied before
inference. Images are resized as upstream's runtime does: multiples of 32 and
at most 160,000 pixels per image. The processor then uses `do_resize=False`.

Output channels follow upstream's action format: left end-effector position
`0:3`, axis-angle `3:6`, gripper `6`; right position `8:11`, axis-angle `11:14`,
gripper `14`; waist `16`, base `17:20`. Remaining channels are padded zeros.
The caller uses its robot kinematics and upstream action-recovery conventions
to turn these relative actions into targets.

For asynchronous execution, supply an unnormalized `(N,60)` action prefix with
`1 <= N <= 30`. The prefix is normalized with the same statistics and its
velocity is frozen during denoising:

```python
actions = model.predict(
    {"images": [ego_rgb, left_wrist_rgb, right_wrist_rgb],
     "action_prefix": pending_actions},
    state=packed_state_60,
)
```

`embodiment_tag` defaults to the sole available normalization entry; set it
explicitly when needed. `action_dim` defaults to 60 for 5B and 7 for RoboCasa.
The action horizon comes from the checkpoint/processor; `action_horizon` is
rejected. `num_steps` defaults to five. BF16 is the validated tier; FP4 and
FP16 requests are rejected. The public API's historical `use_fp8=True` default
is resolved to BF16 for XR-1.

## Native and reference modes

`fuse=False` keeps upstream PyTorch operations and is the reference default.
Experimental `fuse=True` replaces DiT Linear operations with the existing FlashRT hipBLASLt
runner and DiT RMSNorm with the existing wave32 HIP kernel. The runner owns
its algorithm cache and packed weights per model instance. Attention remains
ROCm SDPA; `attention="eager"` is also supported for comparison.

Vision patch Conv3d retains the upstream MIOpen operation. A GEMM replacement
passed synthetic checks but failed on real video frames because its BF16
rounding differences propagated through the VLM; that replacement is excluded.
The native DiT operations can still change BF16 rounding.
Tests compare output shape, finite values, fixed-seed determinism, updated
state behavior, preserved caller RNG, and action cosine/error against the reference. This is a
numerical qualification, not a robot task-success benchmark. By default the
Torch adapters allocate intermediate tensors during uncaptured inference.
Sequential inference is the supported execution pattern for an instance.

## Optional full-model HIP Graph

Pass `use_graph=True` to capture the full vision, VLM prefill and DiT denoising
forward. Both 5B and RoboCasa support this flag, with either `fuse=False` or
`fuse=True`. It is independent of the native DiT kernel optimization:

```python
model = flash_rt.load_model(
    ".cache/xr1/5b", config="xr1", hardware="amd_rdna35",
    num_views=3, num_steps=5, attention="sdpa", fuse=True, use_graph=True,
)
actions = model.predict([ego_rgb, left_wrist_rgb, right_wrist_rgb],
                        "Load washer.", packed_state_60)
```

The frontend captures lazily on the first prediction and retains one graph
profile. Tokens (including same-length prompt changes), image grids, tensor
shapes, embodiment, prefix length and denoise step count form that profile;
changing them releases the old graph and captures a new one. New image, state,
action-mask and prefix values are copied into persistent buffers before every
replay. Noise is regenerated from the observation's `seed` (default 42) using
a private generator, preserving the application's CPU/GPU RNG state. Each
replay recomputes image features and VLM K/V from the current observation.

Capture calls the original model topology. Instance-local helper bindings
prepare static positions, masks and host RNG bookkeeping outside capture;
they are restored afterwards, including on failure. The checkpoint files and
module globals are unchanged. The captured raw actions must exactly equal the
uncaptured forward on the capture input, or setup raises an error. This path
uses the pinned model code and Transformers version described above; it supports
batch-one image-policy inference, not video or training modality tokens.

Preprocessing, input upload, noise generation, action decoding and download
remain outside the graph. First use and every profile change pay for an eager
comparison, warmup and capture. Use a stable prompt/layout in latency-sensitive
loops, and account for that setup separately. `model.pipeline.graph_runner`
exposes `capture_count`, `replay_count` (predictions) and `last_capture_ms` for
diagnostics. For same-instance A/B measurement, the benchmark switches
`model.pipeline.use_graph`; this does not change weights or native adapters.

Run a paired end-to-end comparison (one GPU process at a time):

```bash
OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 \
TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1 HF_HUB_OFFLINE=1 \
python scripts/amd/benchmark_xr1.py \
    --checkpoint .cache/xr1/5b --native --compare-graph --warmup 3 --runs 50 \
    --output results/xr1_graph/5b_native_ab.json
```

The benchmark alternates eager/graph call order on the same loaded model,
checks exact action equality, and records synchronized public `predict`
latency including all preprocessing and transfers. Use `--graph` for graph-only
measurement, or omit both flags for the original uncaptured mode. Startup,
capture time, memory, individual samples and output arrays are saved separately.

Paired gfx1151 measurements on 2026-10-21, BF16, `fuse=True`, SDPA,
five denoise steps, batch one and eight CPU threads:

| Input / checkpoint | Uncaptured P50 / P95 | Graph P50 / P95 | P50 reduction |
|---|---:|---:|---:|
| Synthetic 3×256×256 / RoboCasa | 375.53 / 383.46 ms | 362.69 / 363.91 ms | 3.42% |
| Synthetic 3×256×256 / 5B | 393.67 / 395.51 ms | 367.38 / 371.73 ms | 6.68% |
| Twelve real demo observations / 5B | 653.05 / 656.65 ms | 635.15 / 638.82 ms | 2.74% |

Synthetic cases use three warmup calls and 50 measured calls per mode. The
real case cycles through all twelve observations three times (36 calls per
mode); pass `--observations results/xr1/demo_validation_final.npz --runs 36`
with `--compare-graph --warmup 3` to reproduce it. Every compared action was
exactly equal. These are additional gains over the existing native HIP DiT
path, measured with fresh paired baselines, not the historical table below.

Graph first predictions took 1.85 s (RoboCasa), 1.92 s (5B synthetic), and
3.09 s (5B real), including setup on an already warmed model. Resident PyTorch
allocated memory after warmup increased by approximately 80, 80 and 85 MiB
respectively; this is allocator accounting, not total device memory usage.
The modest latency reduction is consistent with removing host/launch overhead
while retaining the same model arithmetic. It does not establish task success.
Raw evidence is in `results/xr1_graph/*_native_ab.json` and matching NPZ files.

Checkpoint-gated graph regression tests also exercise changed images, states,
seeds, prompts, resolution, denoise steps, 5B prefixes, capture failure recovery,
and caller RNG preservation:

```bash
FLASHRT_XR1_CKPT=.cache/xr1/robocasa FLASHRT_XR1_5B_CKPT=.cache/xr1/5b \
FLASHRT_XR1_OBSERVATIONS=results/xr1/demo_validation_final.npz \

```

For real-camera regression, install `ffmpeg`, download the pinned upstream
demo and check out the reviewed upstream source. Prepare the **demo** checkpoint
with its `load_washer` statistics before running:

```bash
bash scripts/amd/download_xr1.sh demo
git clone https://github.com/XiaomiRobotics/Xiaomi-Robotics-1 .cache/xr1/upstream
git -C .cache/xr1/upstream checkout 0dd7aef8dc87296246aae812a1f59ccb708e5546
python scripts/amd/prepare_xr1_5b.py \
    --checkpoint .cache/xr1/5b --tokenizer .cache/xr1/qwen3vl-tokenizer \
    --stats .cache/xr1/upstream/xr1/configs/data/load_washer.yaml \
    --embodiment load_washer_demo
python scripts/amd/validate_xr1_demo.py \
    --upstream .cache/xr1/upstream \
    --frames 0 40 80 120 160 200 240 280 320 360 400 440
FLASHRT_XR1_5B_CKPT=.cache/xr1/5b \
FLASHRT_XR1_OBSERVATIONS=results/xr1/demo_validation.npz \
python -m pytest tests/test_xr1_rdna35_e2e.py -q
```

The validator uses the demo's camera crops, video start offsets, and matching
robot states. It compares the frontend with upstream runtime utilities and
direct generation on the same ROCm policy, then compares native actions with
the reference. Each native comparison requires cosine > 0.999 and maximum
absolute action error < 0.04; these are regression tolerances, not robot
control limits. The JSON records individual frames and the NPZ preserves
observations for pytest. All twelve reference outputs matched the upstream
runtime preprocessing/direct-generation path exactly on this platform.

Measured on gfx1151 with ROCm `7.2.26015`, PyTorch
`2.10.0+rocm7.2.0.gitb6ee5fde`, Transformers `4.57.1`, three synthetic
256×256 RGB images, five denoise steps, and AOTriton enabled:

| Checkpoint / mode | Warm median | p95 | Output |
|---|---:|---:|---|
| RoboCasa reference | 435.12 ms | 436.75 ms | `(10,7)` |
| RoboCasa native | 360.90 ms | 365.33 ms | `(10,7)` |
| 5B reference | 453.12 ms | 454.37 ms | `(30,60)` |
| 5B native | 377.52 ms | 383.86 ms | `(30,60)` |

The twelve real demo observations gave an aggregate median of 707.17 ms for
reference and 652.80 ms for native mode (three measured calls per frame).
Their native action cosine was at least 0.999851 and maximum absolute action
error was 0.031529. These inputs use the larger camera crops and upstream
bounded resize, so their latency differs from the synthetic benchmark.

Timers include image processing, upload, all model compute, and decoded action
download. Startup and first-call initialization are recorded separately.
Latency is platform-specific and does not establish a real-time control rate
for a robot. Local measurement JSON and test logs live in `results/xr1/`.
